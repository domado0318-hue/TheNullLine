# THE NULL LINE 필요 리소스 및 방향 제안

> 상태: 제작 전 제안 · 2026-10-20  
> 범위: 무한 이동 맵, 주인공 형태, 이를 검증하는 첫 플레이 화면  
> 전제: 현재 게임은 3000×3000 고정 월드와 외곽 벽, 중앙 시작, 단색 사각형 주인공을 사용한다. 아래 항목은 아직 구현되거나 확정된 사양이 아니다.

## 1. 권장 방향

**맵:** 화면 밖 구역을 생성·회수하는 방식으로 끝없이 이동할 수 있게 한다. 바닥 패턴만 반복시키는 화면 효과에 그치지 않고, 이동 방향 앞쪽에 장애물과 적의 활동 공간이 계속 이어지게 한다. 같은 3000×3000 맵의 반대편으로 순간 이동하는 방식은 권장하지 않는다. 추적 중인 적·탄환·경험치가 경계에서 튀는 느낌을 줄 수 있기 때문이다.

**주인공:** **덮개를 쓴 미등록 생존자**를 1순위로 추천한다. 몸을 감싼 낡은 덮개 때문에 머리·팔·다리가 각각 보이지 않는, 둥근 한 덩어리 실루엣이다. 밝은 외곽선과 한 개의 눈빛으로 어두운 바닥과 전투 효과 속에서도 위치가 잘 보이게 한다. 적 AI 로봇은 각진 금속 형태와 다른 색 계열로 두어 즉시 구별한다. 덮개 안의 정체는 처음부터 규정하지 않아도 되므로 기존의 `미등록자` 설정을 기계 주인공 이야기로 바꿀 필요가 없다.

첫 검증은 **주인공 1종 + 반복 가능한 폐역 바닥 1종 + 장애물 2종 + 현재 근접·원거리 적의 형태 구분**으로 충분하다. 실제 이미지 제작 전에는 Phaser 기본 도형으로 실루엣과 화면 가독성을 먼저 확인한다.

## 2. 맵 롤링의 의미와 구현 요구

| 구분 | 제안 |
| --- | --- |
| 플레이 경험 | 어느 방향으로 계속 움직여도 외곽 벽이나 카메라 정지가 보이지 않는다. 주인공은 보통 화면 중심 부근에 있고 바닥과 구조물이 지나간다. |
| 공간 방식 | 일정 크기의 구역을 좌표로 구분하고, 카메라 주변 구역만 생성·표시한다. 멀어진 구역의 표시 객체와 충돌 데이터를 정리한다. |
| 반복감 관리 | 바닥의 기본 패턴은 반복 가능하게 만들되, 균열·번호 표식·시설물 위치를 구역별로 달리한다. 동일한 길목이 즉시 반복된다는 인상을 피한다. |
| 충돌·길찾기 | 벽을 제거하고, 현재 구역과 인접 구역의 장애물까지 충돌·시야·경로 탐색에 반영한다. 구역 경계에 막힌 통로나 장애물 겹침이 생기지 않게 한다. |
| 스폰·회수 | 적은 실제 카메라 밖 안전 지점에 생성한다. 멀어진 적과 탄환은 규칙에 따라 회수하고, 경험치 드롭은 화면을 잠깐 벗어났다는 이유만으로 사라지지 않게 수명 또는 유지 범위를 정한다. |
| 지속성 | 같은 구역으로 되돌아왔을 때 배치가 바뀌지 않도록 구역 좌표와 시드를 사용한다. 파괴한 장애물이나 수집한 아이템이 생기는 시점에는 별도의 상태 보존 규칙을 정한다. |

현재 코드에서 고정 월드를 전제하는 곳은 `src/world/geometry.ts`의 경계 충돌, `src/world/createWorldView.ts`의 외곽 벽과 전체 격자, `src/world/createObstacleLayout.ts`의 전체 맵 배치, `src/scenes/GameScene.ts`의 카메라 경계와 뷰포트 계산이다. `src/enemies/EnemySystem.ts`는 월드 면적으로 적 수를 정하고 월드 전역에서 스폰 지점을 뽑는다. `src/enemies/NavigationGrid.ts`, 전투의 시야·탄환 판정, 경험치 드롭도 구역 경계를 넘는 동작을 확인해야 한다. 따라서 **배경만 스크롤하는 작업보다 범위가 크다.**

구현 시에는 기획자가 조절할 구역 크기(px), 생성·회수 거리(px), 유지할 구역 수(개), 장애물 밀도(개/구역), 적 스폰 범위(px)를 기능별 `src/config/` 파일에 두고 단위를 표시한다. 수치 자체는 플레이 화면 검증 후 정한다.

## 3. 주인공 후보

| 후보 | 형태·움직임 | 세계관 연결 | 판단 |
| --- | --- | --- | --- |
| **A. 덮개를 쓴 미등록 생존자** | 밝은 외곽선이 있는 둥근 덮개. 눈빛 하나와 덮개가 기울어지는 움직임으로 방향·상태를 표시한다. | 등록이 말소된 시민이라는 기존 이야기와 연결된다. 덮개 안의 정체는 열어 둔다. | **추천.** 각진 AI 로봇 적과 실루엣·색이 구분되며 밝은 외곽선으로 위치를 찾기 쉽다. |
| B. 폐기 구역의 생물 | 타원형 몸체와 짧은 촉수/꼬리. 사람의 팔다리가 없다. | 도시 시스템은 정체를 알 수 없는 생체 반응으로 감지한다. | 비인간형이 분명하지만 기존의 시민 등록 말소 설정을 다시 설계해야 한다. |
| C. 등록표만 남은 그림자 | 그림자 덩어리와 떠 있는 등록표. 얼굴 없이 일그러지는 형태다. | 삭제된 시민 기록을 상징한다. | 공포 분위기는 강하지만 초자연적 존재인지 설명이 필요하고, 어두운 바닥에서 윤곽이 흐릴 수 있다. |

**A안의 시각 규칙:** 몸체는 둥글고 부드럽게, 적 로봇은 각지고 단단하게 만든다. 주인공 전용 밝은 색과 끊기지 않는 외곽선을 두고, 눈빛은 적의 공격 신호와 다른 색으로 만든다. 바닥·장애물·적 무리·검 회전·탄환·경험치 효과 위에서도 주인공의 중심과 이동 방향이 보여야 한다. 빨간 피격 점멸 중에도 몸체 윤곽을 유지한다. 무기, HP 바와 경험치 효과가 몸체를 가리지 않도록 한다. 현재 주인공 충돌 크기 `48×48px`를 우선 유지하고, 보이는 외곽과 실제 피격 판정이 맞는지 확인한다.

## 4. 필요한 리소스 목록

| 우선순위 | 리소스 | 첫 제작 범위와 납품 기준 |
| --- | --- | --- |
| 필수 | 주인공 형태 시안 | A·B·C를 AI 로봇 적 옆에 같은 화면 배율로 놓고 흑백 실루엣과 색 대비를 비교한다. 선택한 1종은 위·아래·좌·우 방향과 정지·이동·피격·사망 상태가 구별되게 한다. 도형 프로토타입으로 먼저 확인한다. |
| 필수 | 반복 바닥 모듈 | 폐역/0번 구역의 무채색 바닥 1세트. 상·하·좌·우 이음새가 드러나지 않고, 플레이어·적·경험치 아이콘의 명도가 바닥과 구분되어야 한다. 이미지가 필요해질 때만 타일 텍스처를 제작한다. |
| 필수 | 장애물 모듈 | 통행을 막는 사각 시설물 1종, 원형 시설물 1종. 보이는 외곽과 실제 충돌 형태를 맞춘다. 구역 경계에 걸칠 때의 배치 규칙을 포함한다. |
| 필수 | 구역 표식 | 숫자 `0`, 노선선, 점검 표시 등 작은 바닥 표식 몇 가지. 동일 바닥의 반복을 숨기되 위험 신호나 경험치 아이콘처럼 보이지 않게 한다. |
| 필수 | 적 식별 시안 | 현재 근접·원거리 적 각각 1종. 원래 업무가 읽히는 형태와 공격 전조를 주고 주인공 표시등·색상과 구별한다. |
| 필수 | UI 가독성 기준 | 카메라가 계속 이동하는 중에도 HP 바, 경험치, 무기 선택·재시작 버튼이 고정·식별되는 화면 예시. 기존 UI를 먼저 재사용한다. |
| 후속 | 환경 사운드 | 열차 안내 방송, 기계 작동음, 구역별 낮은 환경음. 먼저 플레이 신호를 가리지 않는 짧은 임시 음으로 검증하고 대사·녹음은 세계관 확정 후 제작한다. |
| 후속 | 구역 변주 | 역사/철거 거리 등 별도 구역의 바닥·장애물·표식. 첫 무한 이동 검증에는 포함하지 않는다. |

이미지 파일을 제작한다면 방향별 프레임, 투명 배경, 기준점, 충돌 범위, 애니메이션 상태 이름을 함께 명시한다. 외부 이미지 리소스를 바로 도입하지 않고, 게임 내 첫 검증은 프로젝트 규칙에 맞춰 Phaser 도형으로 진행한다.

## 5. 제작 순서와 확인 기준

1. **실루엣 확인:** 생존자를 기본 도형으로 그려 현재 적·무기·HUD와 함께 볼 때 즉시 구별되고, 적이 겹쳐도 위치와 방향을 찾을 수 있는지 확인한다.
2. **무한 이동 기본 동작:** 벽·카메라 경계를 없애고, 주인공이 한 방향으로 오래 이동해도 바닥이 끊기지 않게 한다.
3. **구역 연결:** 인접 구역의 장애물·충돌·길찾기를 연결한다. 대각선 이동과 구역 경계 왕복에서 순간 이동, 끼임, 배치 변경이 없어야 한다.
4. **전투·성장 회귀:** 화면 밖 스폰, 적 추적, 탄환, 경험치 드롭·흡수, 피격 밀림, 사망·재시작이 구역 이동 후에도 동작해야 한다.
5. **아트·사운드 확장:** 위 검증을 통과한 뒤 반복 바닥과 캐릭터 애니메이션을 정식 리소스로 교체할지 결정한다.

게임 코드로 옮길 때에는 관련 기존 테스트를 검토하고 구역 경계·왕복·장시간 이동·전투 상태 유지에 필요한 테스트를 보완한다. 실제 브라우저에서 카메라, UI 클릭 좌표, 화면 밖 스폰과 롤링 이음새를 확인한다.

## 6. 결정이 필요한 항목

- 주인공을 **덮개를 쓴 미등록 생존자**로 확정할지. 덮개 안의 정체와 눈빛의 의미는 이후 스토리 작업에서 정한다.
- 구역을 되돌아왔을 때 적·드롭을 얼마나 오래 유지할지. 이 결정이 메모리 사용량과 탐험 감각을 좌우한다.
- `0호선`을 실제 출격 거점으로 쓸지. 채택하면 열차 내부 리소스는 별도 범위로 잡는다.

### 기술 참고

Phaser 3 카메라는 경계를 제거하면 월드 좌표를 따라 계속 스크롤할 수 있다. 반복 배경에는 화면 크기의 TileSprite와 타일 위치 이동 방식도 쓸 수 있으나, 이는 **바닥 표시**에 관한 기능이다. 실제 무한 월드의 장애물·충돌·스폰·회수는 별도로 설계해야 한다. 참고: [Phaser 카메라](https://docs.phaser.io/phaser/concepts/cameras), [Phaser 3 TileSprite](https://docs.phaser.io/api-documentation/3.88.2/class/gameobjects-tilesprite).
