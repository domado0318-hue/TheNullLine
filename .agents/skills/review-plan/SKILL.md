# Review Plan

작성된 구현 계획을 검토하고 개선할 부분을 제안한다.

## 작업 절차

1. 검토할 계획서와 AGENTS.md를 확인한다.
2. 계획과 관련된 기존 코드를 확인한다.
3. 요구사항이 계획에 빠짐없이 반영되었는지 검토한다.
4. 사용자가 해결방안을 제시했거나 계획에 특정 방안이 선택되어 있으면, 그 방안이 각 요구사항을 실제로 해결하는지 독립적으로 평가한다. 더 단순하거나 효과적이고 기존 구조에 잘 맞는 대안이 있는지 비교하고, 더 나은 대안이 있으면 근거·장점·비용 또는 위험을 함께 제시한다.
5. 기존 기능에 미치는 영향과 예상 위험을 검토한다.
6. 구현 단계와 검증 방법이 적절한지 확인한다.
7. 요구사항 → 해결방안 → 구현 단계 → 수정 대상 → 검증 기준의 연결을 대조한다. 누락된 요구사항, 단계에 반영되지 않은 수정 대상, 검증되지 않는 완료 기준, 범위·제외 항목·위험 대응 간 모순이 없는지 확인한다.
8. 발견한 문제와 개선안을 정리한다. 같은 원인에서 나온 문제는 묶고, 구현 전 결정이 필요한 문제와 선택적 개선을 중요도에 따라 구분한다.

## 검토 결과 형식

### 종합 평가
계획의 전반적인 상태를 간단히 설명한다.

### 발견한 문제
- 문제 내용
- 문제가 발생할 수 있는 이유
- 중요도: 높음 / 보통 / 낮음

### 개선 제안
발견한 문제를 어떻게 해결하면 좋을지 설명한다.

### 최종 의견
계획을 그대로 진행해도 되는지,
수정이 필요한지 판단한다.

## 규칙

- 계획 검토 단계에서는 코드를 수정하지 않는다.
- 검토 대상 계획서도 임의로 수정하지 않는다.
- 실제 코드와 요구사항에 근거해 검토한다.
- 사용자의 해결방안을 자동으로 정답으로 간주하지 않는다. 요구사항 충족도, 복잡도, 회귀 위험, 검증 가능성을 기준으로 적합성을 평가한다. 사용자가 특정 방안을 필수 조건으로 지정했다면 임의로 대체하지 말고 해당 조건 안에서 개선점을 제안한다.
- 코드에서 확인한 사실, 사용자 요구, 가정, 제안, 미결 사항을 구분한다. 확인되지 않은 내용을 결함으로 단정하지 않는다.
- 개선안을 제안할 때 관련 절과 수정 대상·검증 기준에도 함께 반영되어야 하는지 확인한다. 최종 응답 전에는 제안한 수정 자체가 다른 계획 항목과 모순되지 않는지 다시 대조한다.
- 근거 없는 문제를 만들어내지 않는다.
- 문제가 없다면 문제가 없다고 명확하게 설명한다.
- 검토가 끝나면 사용자의 다음 지시를 기다린다.
