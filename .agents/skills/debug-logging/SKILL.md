# Debug Logging

버그 원인을 추적할 증거를 얻기 위해 관련 코드에 최소한의 진단 로그를 추가한다. 이 스킬의 결과는 로그와 로그 확인 방법이다. 버그 수정은 별도 작업으로 다룬다.

## 입력 및 범위

사용자가 제공한 버그 증상, 기대 동작, 재현 절차, 관련 기능·파일, 식별 키워드를 확인한다. 빠진 정보는 추정하지 말고 미제공 또는 미확인으로 기록한다. 원인이 알려지지 않았다면 원인 가설을 사실처럼 단정하지 않는다.

허용 범위:

- 관련 실행 흐름을 읽고 원인 가설을 구분할 최소 지점에 진단 로그 추가
- 로그에 필요한 최소 읽기 전용 값 조회
- 기존 로깅 시스템과 설정 사용

이 스킬만으로는 기능 로직, 조건, 반환값, 상태 전이, 오류 처리 방식을 바꾸지 않는다. 임의 Fallback 추가, 예외 무시, 버그 수정, 무관한 리팩터링도 하지 않는다. 로그 값은 읽는 과정에서 상태나 타이밍을 바꾸지 않아야 한다. 부수 효과가 있거나 안전하게 읽을 수 없는 값은 기록하지 않는다.

## 식별 키워드

- 사용자가 지정한 키워드는 철자와 형식을 그대로 유지한다. 임의로 고치거나 다른 키워드를 함께 덧붙이지 않는다.
- 지정이 없다면 증상이 나타나는 기능을 기준으로 짧은 영문 소문자 키워드를 만들고, 여러 단어는 하이픈으로 연결한다. 예: `[movement]`, `[combat-damage]`, `[ui-button]`.
- 원인이 밝혀지지 않은 상태에서 원인 자체를 키워드로 삼지 않는다. 예를 들어 아이템 수량 오류의 원인이 불명확하면 `[memory-corruption]` 대신 `[inventory]`처럼 기능을 나타낸다.
- 한 작업의 모든 신규 진단 로그는 같은 키워드로 시작한다. 별도 작업 ID는 사용자가 지정했거나 기존 작업 정보에서 확인되는 경우에만 추가한다. ID를 임의로 만들지 않는다.

## 코드 분석 및 로그 형식

수정 전에 프로젝트와 관련 폴더의 `AGENTS.md`, 기존 로그 호출과 로그 출력을 확인한다. 관련 기능의 흐름을 진입점 → 주요 입력 → 조건 분기 → 상태 변경 → 외부 호출 → 실패·조기 반환 → 정상 종료 순으로 살핀다. 여러 시스템을 거치면 주요 경계도 확인한다. 가설을 구분하는 데 필요한 위치만 선택하고, 모든 경로에 로그를 추가하지 않는다.

신규 로그 형식은 다음과 같이 한다.

```text
[식별키워드][단계] 메시지 및 주요 데이터
```

단계는 실행 흐름을 찾는 표식이다. 상황에 맞게 `START`, `CHECK`, `BEFORE`, `AFTER`, `WARN`, `ERROR`, `END`를 사용한다. 프로젝트의 `DEBUG`/`INFO`/`WARN`/`ERROR` 레벨은 이 단계와 별개이며, 기존 로깅 규칙을 따른다. 프로젝트에 로깅 도구가 없다면 기존 관례 안에서 가장 단순한 방식을 사용하고 새 로깅 인프라를 도입하지 않는다.

필요한 경우 함수·작업 이름, 주요 입력, 현재 상태, 조건 결과, 변경 전후 값, 실패 사유만 기록한다. 실제 코드에서 확인 가능한 값만 쓰며 비밀번호, 인증 토큰, 개인정보 등 민감한 값은 출력하지 않는다. 반복문이나 매 프레임 실행되는 경로는 출력량과 비용을 검토하고, 같은 로그가 과도하게 쌓이지 않도록 더 상위의 의미 있는 경계나 실제 문제 조건에 로그를 둔다. 이를 위해 기능 동작 조건을 바꾸지는 않는다.

## 로그 위치 확인과 검증

로그를 추가하기 전에 이 프로젝트에서 실제 출력되는 위치를 확인한다. 브라우저 게임이라면 개발자 도구의 Console, 실행·개발 서버라면 해당 터미널, 파일 로깅이라면 코드와 설정에 정의된 파일 경로를 확인한다. `Saved/Logs/*.log` 같은 경로는 실제 프로젝트에서 확인된 경우에만 안내한다. 출력 경로를 확인할 수 없으면 추측하지 말고 확인 불가로 보고한다.

가능한 검증만 수행하고, 저장소 지침에 맞는 빌드·테스트 명령을 사용한다. 이 프로젝트의 게임 코드 변경 검증 지침에 따라 보통 `npm.cmd test`와 `npm.cmd run build` 결과를 확인한다. 사용자가 실제 재현을 요청했거나 재현 환경이 제공된 경우에만 증상을 실행해 확인한다. 빌드 성공은 버그 재현이나 브라우저 로그 출력 확인을 의미하지 않는다.

확인할 항목:

1. 신규 로그가 모두 동일한 키워드와 단계 형식을 쓰는가.
2. 로그가 실제 값만 읽고 기능 동작을 바꾸지 않는가.
3. 민감한 데이터 또는 과도한 반복 출력이 없는가.
4. 프로젝트의 해당 빌드·테스트가 통과하는가.
5. 재현을 실제 수행했다면 기대한 경로에서 로그가 관찰되는가.
6. 로그를 실제 출력 위치에서 식별 키워드로 찾을 수 있는가.

브라우저 콘솔이나 터미널은 해당 화면에서 키워드 검색을 안내한다. 로그 파일은 실제 경로를 확인한 경우에만 PowerShell `Select-String -Path '<확인한 경로>' -SimpleMatch '<키워드>'` 또는 POSIX `grep -F '<키워드>' <확인한 경로>` 예시를 제시한다. 경로를 예시만으로 확정하지 않는다.

## 완료 보고

결과를 다음 항목으로 간결히 정리한다.

- **스킬 경로:** 실제 사용한 스킬 파일의 경로
- **로그 키워드:** 키워드, 사용자 지정/자동 생성 여부, 기능을 기준으로 정한 이유
- **변경 파일과 위치:** 파일 경로, 함수·작업 이름, 로그가 구분할 수 있는 흐름·상태·가설
- **로그 확인 방법:** 실제 출력 위치와 키워드 검색 방법. 경로를 확인하지 못했다면 그 사실을 명시
- **검증 결과:** 실행한 빌드·테스트, 실제 재현 및 출력 확인 여부
- **미검증 항목:** 실행 환경 부재 등으로 확인하지 못한 사항

로그 추가와 버그 수정은 명확히 구분한다. 로그를 추가했을 뿐이면 버그가 해결되었다고 표현하지 않는다. 사용자가 별도로 요청하지 않는 한 Git 커밋을 만들지 않는다.
