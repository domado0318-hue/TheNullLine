# Plan

사용자가 기능이나 변경 사항의 계획을 요청하면 구현 전에 계획을 작성한다. 이 스킬은 계획의 범위와 작성 방식만 다루며, 프로젝트의 코드 스타일이나 기능별 구현 규칙을 새로 정하지 않는다.

## 작업 절차

1. 적용되는 `AGENTS.md`, 관련 코드와 테스트를 확인한다. 계획을 문서로 요청받았거나 구현 참고용으로 지속해서 사용할 계획이면 기존 `docs/` 구조와 관련 문서를 살펴 문서 위치를 정한다.
2. 사용자 요구사항, 원하는 결과, 범위와 완료 기준을 정리한다. 저장소에서 확인한 사실과 사용자가 정한 요구를 구분한다.
3. 계획의 목표나 구현 방향을 크게 바꿀 정보가 빠져 있으면 먼저 간결한 질문을 하고 답을 기다린다. 품질이 낮다·개선이 필요하다처럼 주관적인 평가만 있고 문제로 느낀 지점이 특정되지 않은 경우에도 무엇이 문제인지 먼저 묻는다. 코드나 현재 결과를 살펴보는 것은 사용자의 선호를 대신 추측할 근거가 아니다.
4. 영향이 작은 세부사항만 합리적으로 가정할 수 있다. 이 경우 계획에 가정이라고 표시하고, 확인되지 않은 내용을 사실처럼 쓰지 않는다.
5. 사용자가 해결방안을 제시했다면 요구사항별로 그 방안이 실제로 문제를 해결하는지 평가한다. 더 단순하거나 효과적이고 기존 구조에 잘 맞는 대안이 있는지도 비교한다. 사용자가 특정 방안을 필수 조건으로 지정했다면 임의로 대체하지 않고 그 조건 안에서 개선점을 찾는다. 비교가 계획 방향을 바꾸거나 사용자 판단이 필요한 경우 질문하고, 사소한 선택은 근거와 함께 계획에 반영한다.
6. 요청에 직접 필요한 수정 대상과 구현 단계를 정리한다. 파일 경로와 기존 동작은 확인된 경우에만 특정한다. 아직 알 수 없다면 계획 초기에 확인할 작업으로 쓴다.
7. 계획을 작성한 뒤 요구사항과 해결방안, 구현 단계, 수정 파일, 완료·검증 기준을 서로 대조한다. 요구사항이 빠진 단계, 단계에 없는 수정 파일, 검증 방법이 없는 요구사항, 제외 범위와 충돌하는 항목이 없는지 확인한다. 확인된 사실·제안·가정·미결 사항도 구분한다.
8. 요청된 계획을 채팅 또는 Markdown 문서로 작성해 보여준다. 계획만 요청된 경우 기능 코드를 수정하지 않는다.
9. 계획을 제시한 뒤 다음 지시를 기다린다.

## 계획서 형식

### 목표
무엇을 구현하는가?

### 요구사항
어떤 동작을 만족해야 하는가?

확인된 요구사항, 제안, 가정, 미결 질문을 필요에 따라 구분한다.

### 수정 대상
어떤 파일을 추가하거나 수정해야 하는가?

### 구현 단계
어떤 순서로 작업할 것인가?

각 단계는 확인된 수정 대상, 구체적인 변경 작업, 기대 결과와 해당 단계의 확인 방법을 알 수 있게 쓴다. “개선한다”, “보완한다”처럼 결과가 불분명한 표현만으로 단계를 끝내지 않는다.

### 검증 방법
구현 결과를 어떻게 확인할 것인가?

## 규칙

- 계획 단계에서는 코드를 수정하지 않는다.
- 요청한 범위에 직접 필요한 작업만 필수 계획에 포함한다. 관련 없는 기능, 일반 코드 스타일 변경, 리팩터링을 임의로 추가하지 않는다. 선택적인 제안이 유용하면 필수 범위와 분리해 표시한다.
- 기능 구현에 사용할 계획을 요청받으면 기본적으로 프로젝트의 기존 `docs/` 구조와 형식을 따라 Markdown 파일로 작성한다. 사용자가 채팅에서만 검토하거나 파일을 만들지 말라고 한 경우에는 인라인으로 답한다. 사용자가 경로를 지정하면 해당 경로를 우선하고, 기존 문서 위치가 없으면 저장소의 문서 구조를 확인해 알맞은 위치를 정한다.
- Markdown 계획을 만든 경우 응답에 파일 경로와 핵심 내용을 요약하고, 아직 구현하지 않았음을 알린다. 후속 구현을 원하면 다음 요청에서 그 문서 경로를 지정하면 된다고 안내한다.
- 계획 문서는 후속 작업에 자동으로 적용되거나 자동으로 읽히지 않는다. 사용자가 그 계획에 따라 구현을 요청하면 해당 문서를 다시 읽고 현재 코드와 대조해 범위를 따른다. 자동 연결을 원하면 적절한 연결 위치를 설명한다. 프로젝트 전반의 규칙을 바꿀 필요가 있을 때는 대상 파일과 구체적인 문구를 먼저 제안하고, 승인 전에 `AGENTS.md`나 다른 스킬을 수정하지 않는다.
- 계획을 작성한 뒤 사용자의 다음 지시를 기다린다.
